# Протокол финальной проверки на test (pre-registration)

Документ заполняется и замораживается ДО запуска test (`python3 freeze_test.py`). После заморозки его не правим:
изменение файла сломает заморозку, и check.py откажется запускать test. Результаты — отдельно, в TEST_RESULTS.md.

## 1. Зачем
Все решения (думание, ключ, промпты, второй голос, модель доверия, порог) принимались на dev. Оценка на dev поэтому
оптимистична: мы выбирали под эти 51 работу. Test — 27 работ, которые ни разу не проверялись моделью; только он даёт
честную оценку того, как система сработает на новых домашках.

## 2. Данные
- Test: 27 работ, 596 размеченных задач, из них 98 с ошибкой (data/splits_new.csv, data/labels.csv); ещё 31 задача
  в списке проверки без метки (начато и брошено / зачёркнуто) — в метрики не входит. freeze_test.py сверяет эти числа
  с labels.csv и не заморозит test при расхождении.
- Разбиение по заданиям: ни одно задание (task_key) не встречается и в dev, и в test. 42 задачи test — те же задачи
  задачника, что в dev (другое задание, другие ученики, data/test_overlap.csv): основные метрики — на всём test,
  дополнительно — «test без повторов из dev» (строка в --report).
- 4 из 13 учеников есть и в dev, и в test (leakage_audit.py). Для LLM это не утечка; для модели доверия проверено на
  dev группировкой по ученикам — качество то же (ноутбук, раздел 4).
- История разметки test (все правки — до любого запуска модели на test и без её вердиктов; снимки
  data/labels_before_*.csv, `leakage_audit.py`, раздел 5):
  1. аудит по ключу — 2 метки (ошибка найдена: 1 → 0);
  2. перевод на правила от 26.09 — 9 меток (0 → 1: неверно выписанный ответ при верном решении, не сделан последний
     тривиальный шаг);
  3. 28.09 эти 9 меток перепроверены по уточнениям от 27.09 («неверно выписанный ответ не ошибка, только если
     выписанное число есть в решении»; «найдена не та величина, нужен ещё содержательный шаг — ошибка»). 8 остаются
     1: в ответе промежуточное число или результат лишнего верного шага (W044 17-Б2-3, 17-Б2-4), не извлечён корень
     (W039 Б2-11.2, Б2-11.5, W067 В1-6), не досчитано 180° − угол или сумма (W044 17-Б1-12, 15-Б2-8), отношение не
     переведено в «во сколько раз» (W039 Б1-3.1). Одна метка снова «ошибка» (1 → 0): W044 15-Б2-21 — найдена высота, а
     нужна площадь (как W031 Б1-16 в dev: найдена гипотенуза, нужен радиус; проверяющий зачеркнул ответ).
  Остальные уточнения от 27.09 (описки, обоснования в доказательствах и т. п.) к test целиком не применялись: test
  размечен по правилам от 26.09. На dev при разборе промахов исправлено 7 меток из 883: 4 — по уточнённым правилам
  (W015 5а, W053 В1-3а, W054 В1-1в, В1-1д), 3 — ошибки разметки (W013 2а, W024 5.13, W060 6).
- Разметку test после просмотра вердиктов модели НЕ исправляем (п. 7).

## 3. Что замораживается (reports/test_lock.json + git-тег before-test)
- Код и настройки: check.py, config.json (набор final), этот протокол.
- Данные: labels.csv, answer_key.csv, splits_new.csv, works.csv, test_overlap.csv, work_map.csv.
- Модель доверия и код признаков — через `--extra` (команда в п. 6).

## 4. Система
- Проверка: Gemini 3.8 Flash, набор `final` из config.json — распознавание minimal (промпт v1), проверка low (промпт v1)
  с эталонными ответами из data/keys/answer_key.csv, без двойного распознавания.
- Модель доверия: логистическая регрессия на 4 признаках — вердикт, спор вердикта с ключом, разборчивость почерка,
  тревога без названных ошибок (ml/trust_features.py); среднее 100 моделей фолдов (ml/trust_model.pkl), порог из
  ml/trust_threshold.json. Задача с вероятностью выше порога или без вердикта уходит куратору.
- Второй голос (DeepSeek) в систему не входит: на dev не дал выигрыша (ноутбук, раздел 3).
- Список задач работы для проверки берётся из разметки (номера задач с решением или пометкой, включая 31 задачу без
  метки), как и на dev. В работе его заменяет список заданных задач от репетитора (`check.py --scope-file`, на test
  запрещён); поиск задач в тетради эта оценка не измеряет. Признак «тревога без названных ошибок» оценивается в том же
  режиме, что и на dev.

## 5. Метрики и гипотезы
Все метрики — с 95% bootstrap-интервалом по работам.

Первичные — проверка без куратора, все 596 задач (задача без вердикта считается несовпадением): совпадение
вердиктов, recall (доля найденных ошибок учеников), доля ложных тревог, precision (`python3 check.py --report`,
строка test).

Модель доверия (`python3 ml/apply_trust.py --split test`): доля задач к куратору и итоговое совпадение при условии,
что куратор решает свои задачи верно. Порог выбран ТОЛЬКО на dev процедурой Learn then Test так, чтобы доля задач,
где проверка ошиблась и куратор этого не увидел, была ≤ α = 2% с вероятностью ≥ 90% (δ = 0,1).

Вторичные: те же метрики «без повторов из dev»; цена на работу, ₽; доля задач к куратору с учётом 31 задачи без метки
(`features.py --include-unlabeled` → `ml/apply_trust.py --wide data/features_wide_all.csv`; на dev 12,4% вместо 7,2%).

Анализ чувствительности: 12 правок меток test до запуска (п. 2: 2 по ключу, 9 по правилам от 26.09, 1 при
перепроверке); 2 по ключу, который система сама использует, могут завышать её совпадение с разметкой. Дополнительно считаем метрики по разметке на каждом
этапе правок (`python3 label_sensitivity.py --split test`) и сообщаем все цифры. Для справки: на dev эффект всех
правок разметки — +1,3 п.п. совпадения (95,1% → 96,4%), и это нижняя оценка смещения.

Ожидания, объявленные заранее (результат публикуется в любом случае, даже если хуже). Гипотеза считается
выполненной, если выполнена для точечной оценки; интервалы сообщаются рядом. Ориентиры dev — в скобках:
- H1: совпадение вердиктов проверки на test ≥ 92% (dev: 96,4% [95–98]; по исходной разметке 95,1%);
- H2: recall на test ≥ 90% (dev: 97,4%);
- H3: итоговое совпадение с учётом куратора ≥ 97,5% при доле задач к куратору ≤ 15% (обе доли — от 596 размеченных)
  (dev, out-of-fold: 98,8% [98,1; 99,4] при 7,2% [3,8; 12,1] к куратору; вложенная CV с выбором v1/v2 внутри фолда:
  98,6% при 7,2%);
- H4 (вторичная, про порог): доля задач test, где проверка ошиблась и куратор не увидел, ≤ α = 2%; сообщаем и
  верхнюю 90%-границу Клоппера–Пирсона (формально — без учёта группировки задач).

## 6. Порядок и правила
1. Все правки кода закоммичены; `python3 -m unittest discover tests` и `python3 leakage_audit.py` без проблем.
2. Ноутбук ml/trust_model.ipynb перезапущен на этой машине (модель пересохранена под её версию scikit-learn), затем
   заморозка: `python3 freeze_test.py` (модель доверия, порог и код признаков добавляются в заморозку автоматически).
3. Запуск (один раз; Мак не должен засыпать):
   `caffeinate -i python3 check.py --preset final --split test --works all`
4. Технический сбой (баланс, пустой ответ, неразобранный ответ, обрыв сети) — дозапуск той же командой (кэш не тронет
   готовые работы) или `python3 check.py --reparse --tag low_key` для сохранённых неразобранных ответов. Это не
   отклонение. Каждый запуск пишется в reports/test_runs.log.
5. Отчёты: `python3 check.py --report`; `python3 features.py && python3 features_wide.py`;
   `python3 ml/apply_trust.py --split test` (сверяет, что в таблице признаков 596 задач и 98 ошибок, и печатает число
   ошибок проверки — оно должно совпасть с несовпадениями в строке test у `--report`);
   `python3 features.py --include-unlabeled --out data/features_all.csv && python3 features_wide.py --features
   data/features_all.csv --out data/features_wide_all.csv --runs g_low_key && python3 ml/apply_trust.py --split test
   --wide data/features_wide_all.csv`; `python3 label_sensitivity.py --split test`.
6. Ничего не меняем в коде, промптах, config.json, ключе, разметке и модели доверия после начала test. Если без этого
   нельзя (баг, из-за которого часть test не проверяется), — `python3 freeze_test.py --amend "причина"`: изменение
   попадает в reports/test_deviations.log и описывается в TEST_RESULTS.md.
7. Явную ошибку разметки test, найденную после запуска, не исправляем тихо: сообщаем обе цифры — по исходной
   разметке (основная) и по исправленной (дополнительная), с перечнем исправленных задач.
8. Записать результаты в TEST_RESULTS.md: строки test и «test без повторов из dev», вывод apply_trust и
   label_sensitivity, сравнение с H1–H4, разбор промахов test так же, как dev (error analysis).
